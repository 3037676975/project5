这次 Project5 的问题不是 Git 本身坏了，而是正常代码部署流程被错误地和 Nginx 自动修改绑在了一起。 最近一次稳定成功的提交是 F4A24EF，对比它和后续失败版本后，问题才真正定位出来。

一、当时出现了什么现象

宝塔能看到 Git 提交，甚至日志里已经显示代码拉取成功，但最终部署仍然标红，浏览器里的前端也没有更新。

Git pull 成功
↓
8005 新进程启动
↓
自动修改宝塔 Nginx
↓
nginx -t 报错
↓
部署失败
↓
公网继续显示旧页面

二、为什么一开始一直没找准

前面一直盯着“Git 有没有拉最新”“8005 有没有旧进程”排查，这两个方向都没错，但不是最终根因。

真正有效的办法是：找到最后一次明确成功的提交，然后和失败版本做差异对比。

版本部署特点结果
F4A24EF宝塔负责 git pull；部署脚本只负责重启程序和验证前端成功
后续版本又增加了自动修改 Nginx、检查公网入口等步骤连续失败

三、真正的根因

根因：把“应用发布”和“基础设施配置修改”放进了同一条自动部署链路。

后续脚本会在每次 Git 部署时自动修改宝塔 Nginx 的 location /。真实服务器配置里还有 include、反向代理文件等结构，脚本处理不完整时就会出现：

nginx: [emerg] duplicate location "/"

Nginx 检查失败后脚本会回滚配置，所以服务器不会彻底坏掉，但本次部署会失败，公网入口仍然保持旧状态。

四、最终正确的修复方式

① 宝塔 Git 插件先执行 git pull
② 部署脚本读取当前 commit
③ 杀掉 Project5 旧进程，释放 8005
④ 启动当前代码的 app.entry:app
⑤ 验证前端、静态资源和运行 commit
⑥ 模型检查放后台执行，不阻塞网页切换
关键决定：正常部署不再自动修改 Nginx。Nginx 修复脚本保留，但只作为单独的一次性维护工具，需要时再执行。

五、以后遇到同类问题怎么排查

先找“最后一次成功”

不要从最新失败版本开始猜。先找到最后一次成功 commit，再比较后续修改了哪些部署文件。

把部署分成三层

代码已更新
≠
进程已更新
≠
用户访问到的新版本

但是不要让每次部署都改基础设施

端口、Nginx、SSL、域名等属于基础设施配置。它们应该独立维护，不应该每一次业务代码提交都自动重写。

六、给其他 AI 的排查提示

如果 Project5 宝塔部署连续失败：

1. 先找到最后一次成功 commit：F4A24EF。
2. 对比成功版本和当前版本的部署脚本，不要先猜模型或 GitHub 故障。
3. 正常发布链路只保留：git pull → 停旧进程 → 启动 8005 → 验证当前 commit。
4. 不要在每次自动部署时修改 Nginx。
5. 如果需要修 Nginx，把它作为独立维护动作处理。
6. 判断成功时必须区分：
   - Git HEAD 是否最新
   - 8005 是否运行最新 commit
   - 用户访问入口是否已经指向正确服务
7. 优先恢复最后一次已知成功的最小部署路径，再逐项增加功能。
一句话经验：
部署系统越关键，越要保持最小化。业务代码发布只负责“拉代码、换进程、验版本”；Nginx 之类的基础设施修改不要混进每一次自动部署。
